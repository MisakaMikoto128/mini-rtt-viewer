# UI 技术栈评估(ADR-11 素材)

背景:Slint 开发体验问题累积(见 ADR-4),用户提出"不如放弃"。本文是迁移评估,
结论供决策,不预设立场。

## Slint 实证痛点(本项目 30+ 条踩坑,摘主要)

1. **布局约束反直觉**:HorizontalLayout 收缩语义不可靠(min-width:0 无效)、
   Flickable viewport 内部托管劫持外部绑定、非布局父下 VerticalLayout 高度塌陷
   —— 多轮返工都栽在布局
2. **样式定制 hack**:浅色美化必须 include-path 覆盖内置 styling.slint 单文件,
   且改动不触发重编(假构建陷阱)
3. **跨语言能力受限**:1.17 不为 public function 生成 Rust 方法,数据流全靠
   changed 回调链拼
4. **生态小**:搜索框/虚拟列表/右键菜单全部自研(行模型、选中层、滚动量化、
   列级复制都是手搓,没有可复用的现成组件)
5. **可视化调试弱**:VS Code 预览不含 style-override 与真实数据,调 UI 靠截图+UIA
6. 坑无社区沉淀:同类问题基本搜不到答案,全靠自己趟

## 候选栈

| 栈 | 优势 | 代价 | 契合度 |
|----|------|------|--------|
| **Tauri 2 + Web 前端** | 生态最大,CSS 布局零坑,DevTools 调试,热重载;Web 技术永不过时 | WebView2(Win10/11 系统自带);包体 +几 MB;Rust⇄前端 IPC 一层 | 高:"表单 + 文本流"正是 Web 舒适区;虚拟列表/搜索高亮/选中复制全是现成方案 |
| **egui** | 纯 Rust,即时模式调试直观,无布局坑 | 500 行日志每帧重画需自管虚拟化;默认观感朴素;文本选择/复制弱 | 中:文本流渲染要自己优化 |
| **iced** | Elm 架构,纯 Rust,声明式 | 生态中等;复杂文本交互(选中/复制/搜索高亮)同样要自造 | 中:换汤不换药风险 |
| **留 Slint** | 25 条 FR 全部已实现且稳定;坑已趟完(AGENTS.md 30+ 条) | 每次新 UI 需求都可能再踩新坑 | 现状延续 |

## 关键事实:迁移成本被架构大幅降低

数据路径(FFI/解码/ANSI/断行/换行/搜索/偏好)已按 ADR-7 收敛在纯逻辑层
(`jlink_dll.rs`/`log_model.rs`/`ansi.rs`/`config.rs`/`rtt.rs`),**不依赖 Slint
类型,可整体复用**。迁移工作量 = 前端重做(布局 + 交互绑定),核心逻辑零改动或
最小改动。

## 建议(供 ADR-11 决策)

1. **不立即重写**:现有功能稳定运行,重写最大风险是 25 条 FR 回归
2. **先做验证性 spike**(不动现有代码):Tauri 2 骨架 + 接 log_model 数据层 +
   日志虚拟列表 + 搜索高亮,量化 体积/启动/滚动流畅度/开发速度,一周内出数据
3. **立项触发条件**:Slint 再导致 2-3 次"布局/样式多轮返工"(即再消耗一个
   整轮的 UI 修复),或 spike 证明 Tauri 全面优于现状
4. spike 通过后整体切换,Slint 版本以 0.1.x 最后一个 tag 归档
